# 项目原则（Project Principles）

本文定义 KanBan ToDo monorepo 的工程原则，作为模块设计和后续迭代的基线。

## 1. 共享契约优先

- 业务数据契约先落在 `shared/src`，再由 `client` / `server` 消费。
- 禁止在前后端重复定义同一业务模型，避免字段漂移。
- 契约变更按“跨模块变更”处理，必须评估兼容性与迁移影响。

## 2. 本地优先体验

- 客户端应在弱网或断网情况下继续可用（依赖 `IndexedDB`）。
- 用户操作优先写入本地，再通过同步机制与服务端对齐。
- 同步机制目标是最终一致性，不阻塞核心交互流程。

## 3. 模块边界清晰

- `client`：界面、状态管理、本地存储、同步编排。
- `server`：认证鉴权、API/WebSocket、服务端持久化。
- `shared`：类型、枚举、通用日期工具。
- `release`、`_recovery`：产物与恢复数据，不属于业务实现模块。

## 4. 数据演进非破坏

- Schema 演进优先保证用户数据可保留。
- IndexedDB 升级采用“补齐缺失 store/index”策略，默认不做破坏性清理。
- PostgreSQL 结构以 `server/src/database/schema.ts` 为事实来源，变更需可追溯。

## 5. 安全基线

- 服务端默认全局 JWT 鉴权，仅 `@Public()` 路由可匿名访问。
- 敏感配置统一使用环境变量（`JWT_SECRET`、`DATABASE_URL`、`SMTP_*` 等）。
- 功能开发不得绕过所有权校验或削弱现有鉴权链路。

## 6. 工程可维护性

- 根目录 workspace 脚本是标准入口，避免分散启动方式。
- 保持职责单一：UI 在 `client`，领域服务在 `server`，契约在 `shared`。
- 继续沿用 `services/stores/composables` 分层，避免隐式耦合。

## 7. 交付前质量门禁

- 至少执行：
  - `npm --workspace client run type-check`
  - `npm --workspace client run lint`
  - `npm --workspace server run build`
- 至少手测：登录、看板拖拽、习惯打卡、同步链路。

## 8. AI 编码约束（Vibe Coding Rules）

- **只做被要求的事** — 不擅自重构、优化、扩展未提及的代码。
- **先读后写** — 修改任何文件前必须先读完相关上下文，遵循已有模式。
- **不引入幻觉** — 不使用未安装的依赖、不编造不存在的 API 或方法。
- **不过度工程** — 三行能解决的不抽函数，一次性逻辑不建抽象层。
- **不留垃圾** — 禁止残留 `console.log`、注释掉的旧代码、空 TODO、调试临时文件。
- **不加废话注释** — 代码自解释即可，只在逻辑不直观处加注释。
- **不膨胀依赖** — 能用现有依赖或原生实现的，不引入新包。
- **控制文件长度** — 单文件超过 500 行时必须考虑拆分。当一个文件持续增长，说明它承担了过多职责，应将独立的功能块提取为单独的模块或组件，而不是在同一个文件里不断追加代码。
- **不破坏现有模式** — 项目已有的命名、分层、风格约定必须沿用，不另起一套。
- **不假装完成** — 每行代码必须是可运行的实现，禁止 placeholder 或空壳函数。
- **交付前自查** — 改完后验证类型检查通过、无遗留调试代码、不影响已有功能。
